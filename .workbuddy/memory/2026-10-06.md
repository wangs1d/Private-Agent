3. **麦克风上行未验证**：VAD 阈值 350 RMS（`endpoint-detector.ts:35`），
   麦克风音量偏低时永不触发断句 → 说了没反应。客户端日志无 VoiceDuplex debugPrint，
   说明 startMic 没报错，最可能是采集音量不足或 Windows 麦克风隐私设置。

   上次通话未走 `end()` 时卡在 true → 下次不再重建 duplex（表现：接通但永远没声音）。

## 「通话接通了但说话没反应」根因修复（第二轮）

用户反馈说话没反应、怀疑 VAD。实测定位到三个叠加原因：

### 根因 1（致命，100% 必现）：TtsPlayer.isPlaying 永久为真
`isPlaying => _player != null`，而 `_player` 只在 stop/dispose/开新播时置 null；
正常播完只走 `_fireCompletion()`，从不释放 → 播过一次 TTS 后 isPlaying 恒 true。
`voice_duplex_service` 的上行门控 `if (_micGated || TtsPlayer.instance.isPlaying) return;`
因此永久丢弃麦克风。上一轮加的接通问候语正好保证每次通话必先播 TTS。

修复（client/flutter_app/lib/core/services/tts_player.dart）：
- onPlayerComplete / stopped 走 `_handlePlaybackEnd(seq)`：先 `_disposeCurrent` 再 fire 完成回调
  （顺序不能反，依赖 isPlaying 归位的 consumer 才能拿到正确值）
- `_playSeq` + `_firedSeq` 代次去重，避免 stop() 抢占 / 双通道重复下发
- `_disposeCurrent` 先摘 `_player` 引用再释放，防并发误伤新播放
- 新增 `addOnPlaybackStarted` 广播：`agent.phone.voice_reply`（问候语）这条不走 duplex
  的播报路径此前完全没通知门控，会把问候语回采成自激
- `addOnCompleted` 加去重（main.dart 有 3 处 add、1 处 remove，会累积）
副作用：简报窗 `_onCardClicked` 原先因 isPlaying 恒真导致「点击永远只能停止、无法重播」，一并纠正。

### 根因 2：VAD 绝对阈值判定太脆弱
实测（探针 .scratch/probe-vad-threshold.cjs）：
| 电平 | 旧(阈值350) | 新(自适应) |
|---|---|---|
| RMS 120 | 不触发 | 不触发 |
| RMS 300 | **不触发** | **触发 5.2s 应答** |
| RMS 800 | 触发 | 触发 |
| RMS 2500 | 触发 | 触发 |

修复（server/src/services/voice-duplex/endpoint-detector.ts）：
- 绝对下限 350 → 200（可用 `VOICE_VAD_SPEECH_THRESHOLD` 覆盖）
- 新增自适应：跟踪背景噪声（未判为语音块的 RMS 20 分位），生效阈值 = max(200, 底噪×3)
  安静房间压低门槛、嘈杂环境自动抬高抑制误触发
- 底噪估计故意跨句保留（reset 不清），否则每句话都要重新收敛

### 根因 3：链路完全不可观测
- 服务端每 5s 打 `vad probe bytes=… noise=… inSpeech=… → 结论`（含返回值/troubleshoot 提示）
- 非 listening 态超过 30s → 看门狗强制回 listening（此前会永久丢弃上行）
- 客户端同步诊断阈值口径 350 → 200

## 通话响应延迟分析与优化（第三轮）

用户反馈「能通了但回复迟缓」。实测（3s 语音 + 断句，探针 .scratch/probe-latency.cjs）：
说完 → 收到语音帧 = 3748ms。服务端打点拆解：

| 段 | 耗时 | 性质 |
|---|---|---|
| MiniMax 上游首包语音 | 1843~2189ms | **外部不可控**（ASR+LLM+TTS），占 ~58% |
| VAD 尾部静音 | 700ms（已改 550ms） | 可调，含 100ms 粒度误差 |
| 等整轮生成完才下发 | 0~931ms（浮动） | **可优化**：流式分片可消除 |
| 上行音频推送 | 144ms（改前 740ms） | 已优化 5 倍 |
| WS 传输 310KB base64 | ~480ms 含客户端解析 | 本地回环，非瓶颈 |

### 已做的优化
1. `minimax-realtime-service.ts` dispatch：块间 sleep 20ms → 4ms。原实现混淆了
   「实时流输入」和「VAD 已录完整句回放」，导致推送耗时随句长线性增长
   （3s 话白等 740ms，10s 话白等 2s）。抽成 `REALTIME_INPUT_CHUNK_DELAY_MS`，
   可用 `MINIMAX_REALTIME_INPUT_PACE_MS` 覆盖（设 0 = 尽快推完）。
2. `minimax-duplex-session.ts`：静音判说完 700ms → 550ms，抽成
   `DEFAULT_ENDPOINT_SILENCE_MS`，可用 `VOICE_ENDPOINT_SILENCE_MS` 覆盖。
3. 加延迟打点日志：`VAD 断句 Xs 音频，将分 N 块推送` / `回合完成：推送 Xms →
   首包语音 Yms → 整轮 Zms（回复 Ns 音频）`，超过 800ms 的整轮等待会打 ⚠。
   这两个打点是后续排查延迟的第一手依据。

### 待办（未做，需权衡）
流式分片下发：miniMax 是流式返回 delta，但 `turn()` 等 `response.done` 才 resolve，
服务端再攒成一整个 tts.chunk 下发。改成按句/按时长分片可消除 0~931ms 等待，
但 Windows 端 audioplayers 每片要写临时文件，片间会有 50~100ms gap。
建议方案：短回复（≤2.5s 音频）一次性下发保无 gap，长回复才分片。

## 排查：手机端邮箱登录「获取验证码」报网络错误

- 结论：不是服务端业务错误。客户端 `email_login_api.dart` 的 catch-all 兜底文案
  「网络错误，请检查网络后重试」覆盖了所有异常（DNS/拒绝连接/15s 超时/TLS/响应非 JSON）。
  服务端真实错误各有专属文案：503=邮件验证通道未开启、502=邮件发送失败、429=限频、
  403=白名单拦截 —— 都不会显示成「网络错误」。
- 三个根因候选：
  1. `client/flutter_app/build_apk.ps1:6` 只有 `flutter build apk --release`，未传任何
     `--dart-define` → `ApiConfig.httpBase` 回落 `http://127.0.0.1:3000`，真机上指向手机自身
     → 连接被拒。（对比 `build_windows.ps1` 有 `-HttpBase` 参数）
  2. `EmailLoginApi` 用 `ApiConfig.httpBase`（本地 runtime），而账号/OTP 属控制面
     （其他账号类 API 如 feedback/inbox/register 都走 `ApiConfig.controlPlaneBase`）。
     手机端邮箱登录基址选错，烤 CONTROL_PLANE_URL 也不生效。
  3. `android/app/src/main/res/xml/network_security_config.xml`：`base-config` 禁明文，
     白名单仅 192.168.10.2/3、10.0.2.2、localhost、127.0.0.1。后端若是 http:// 其它 IP 或
     域名（如 login.nextbot.top）会被系统拦截 → 网络错误。应改 https 或加白名单域名。
- 附带发现的代码 bug：`mobile_ui/mobile_login_page.dart:275、313` 用 `widget.api`，
  但 `MobileLoginPage` 类无 `api` 字段（只有 onLoggedIn/onDebugSkip），state 内是 `_api`
  → 悬空引用，编译会报错，需确认当前代码状态。
- 排查手段：logcat 过滤 `[EmailLoginApi] startOtp failed:` 看异常类型
  （SocketException / TimeoutException / FormatException=响应非 JSON / HandshakeException）。

## 构建尝试失败：Dart 无法创建子进程（OS error 231）
- 现象：任何 `flutter` 命令都崩，报 `ProcessException: 所有的管道范例都在使用中
  (process_win.cc:742)`，OS error code 231（ERROR_PIPE_BUSY）。
- 已排除：不是沙盒（dangerouslyDisableSandbox 同样失败）、不是 MSYS（PowerShell 同样失败）、
  不是残留进程（dart/java 进程数均为 0）、git 本身可用（`git -C /d/Flutter log` 正常）。
- 已验证：写最小 dart 脚本跑 `Process.run('cmd',['/c','echo',...])` → i=1、i=2 全部 FAILED 231。
  结论：该会话环境下 Dart VM 无法创建任何子进程，flutter/gradle（FlutterTask 会回调 flutter）
  都无法运行，构建只能在用户自己的终端里做。
- 有用发现：加 `--no-version-check` 可跳过 `checkFlutterVersionFreshness` 里的 `git log`
  调用（flutter_command_runner.dart:450 受 `version-check` flag 控制，默认 true），
  能把崩溃点从 git 挪到 Gradle；但 Gradle 启动同样 231。已把该开关写进 build_apk.ps1。
- 待用户在自己终端执行（`client/flutter_app` 下）：`.\build_apk.ps1`
  （自动探测局域网 IP 192.168.10.2 并烤入 HTTP_BASE/CONTROL_PLANE_URL）。

## 根源修复：线程内部帧泄漏到手机端聊天气泡（[上一轮回复中断…[不可信内容围栏…]）
- 定性：不是「电脑端离线的对话兜底」。两类文本都是**写给 LLM 的线程上下文帧**，
  泄漏到了用户可见气泡：
  - `[上一轮回复中断…]` = `external-model/chat-thread-store.ts` buildInterruptedToolChainNotice
    （工具链未收尾时的防串台占位帧）
  - `[不可信内容围栏 source=tool:x]` = `external-model/untrusted-content.ts` fenceUntrustedToolContent
    （工具结果进消息流前的 prompt injection 围栏）
  - 两段黏在一起的直接成因：占位帧生成时把 tool 消息首行原样摘录，而首行恒为围栏头。
- 泄漏链路：占位帧以 role:"assistant" 待在线程里 → 模型下一轮当「自己说过的话」复读
  → 流式通道直穿；且 `tool-result-processor.ts` 旧守卫只是「跳过渲染路由」却
  `return humanize(text)` 原样放行；手机端 `mobile_chat_controller` 零清洗（连桌面端
  已有的 [ts:]/DSML 清洗都没接）。
- 修法（治本 + 三道防线，均已落地并通过 tsc + 回归测试）：
  1. 新增 `server/src/external-model/internal-frames.ts`——内部帧唯一权威契约
     （INTERNAL_FRAME_TAGS / isInternalFrameText / stripInternalFrames /
     stripInternalFrameMarkup / INTERNAL_FRAME_PREFIX_RE）。此前名单在 3 处各写一份且
     都不完整，新增帧必漏，这是根因。
  2. thread 层：占位帧摘录前先剥围栏标签外壳（保留块内真实数据作为「已办事实」），
     并在帧内钉死「禁止原样或改写后复述给用户」；内部帧不进 recap 待归纳区。
  3. 出口咽喉：`stream-chat-helpers.stripInternalControlTags` /
     `createStreamControlTagSanitizer` 接入契约（跨 chunk 缓冲吞半截标签），
     WS chunk 唯一出口 `chat-user-message.ts sendAssistantChunk` 再拦一次。
  4. ToolResultProcessor：整条是内部帧 → 返回 ""（真不展示）；混排 → 剥帧留正文。
  5. 客户端：`assistant_text_sanitizer.dart` 增 stripInternalFrames（名单与服务端对齐），
     手机端 chunk/done/bubbles 三处接入清洗；整轮只剩内部帧时撤掉空占位泡不留空白气泡。
- 回归：`server/test/internal-frames.test.ts`（7 例，含端到端折叠用例）；
  既有 thread/recap/渲染类 57+113 例全绿。
- 注意：Dart analyze 在本机仍无法启动（管道报错），客户端改动未做静态校验。
